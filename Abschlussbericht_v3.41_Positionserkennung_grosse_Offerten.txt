1. AUSGANGSLAGE
================================================================

Rueckfrage des Betriebs nach Version 3.40: nachdem die dort gebaute
ehrliche MAX_TOKENS-Meldung das gemeldete, 13-seitige, rund 90
Positionen zaehlende Offerte-PDF (Offerte_18191_Steildachsanierung_
Alpeneggstrasse_22_Bern) sauber und ohne erfundene Positionen
abgelehnt hatte, kam per Bildschirmfoto die naheliegende Gegenfrage:
"koennen wir das verbessern?" - also nicht nur sauber scheitern,
sondern fuer ein Dokument dieser Groesse tatsaechlich erfolgreich
erkennen.

Ein echter Gemini-Aufruf ist in dieser Sandbox nicht moeglich - die
Diagnose stuetzt sich deshalb auf Googles eigene Dokumentation zum
verwendeten Modell (gemini-3.6-flash), nicht auf eine Vermutung:

  1. maxOutputTokens: 8192 (aus v3.40) war fuer den gemeldeten Fall
     zwar rechnerisch ausreichend, aber ohne echten Sicherheitsabstand
     fuer dichtere reale Dokumente.
  2. Ein bisher unberuecksichtigter zweiter Verbraucher desselben
     Budgets: Googles eigenes Forum dokumentiert ausdruecklich, dass
     "Gemini 3 Flash and Flash-Lite … also do not support full
     thinking-off" - bei dieser Modellgeneration kann unsichtbares
     "Denken" Token aus demselben maxOutputTokens-Budget verbrauchen,
     aus dem auch die eigentliche JSON-Antwort kommt, obwohl das reine
     Ablesen einer Tabelle keinerlei erweitertes Schlussfolgern
     braucht. Ein Teil der 8192 Token aus v3.40 stand der eigentlichen
     Positionsliste damit moeglicherweise nie zur Verfuegung.

2. TATSAECHLICH UMGESETZTE AENDERUNGEN
================================================================

2.1 Edge Function extract-offer-positions - v12 auf v13
----------------------------------------------------------
Zwei Zeilen im generationConfig-Block, keine neue Infrastruktur:

  generationConfig: {
    maxOutputTokens: 65536,
    thinkingConfig: { thinkingBudget: 0 },
    responseMimeType: "application/json",
  },

  1. thinkingConfig:{thinkingBudget:0} - reduziert das unsichtbare
     Denken so weit, wie das Modell es zulaesst (Google dokumentiert
     ausdruecklich, dass diese Modellgeneration es nicht vollstaendig
     abschalten kann; die Einstellung ist trotzdem gesetzt, um so viel
     wie moeglich davon dem eigentlichen JSON-Ausgabebudget
     zurueckzugeben).
  2. maxOutputTokens 8192 -> 65536 - keine erneute freihaendige
     Schaetzung, sondern die von Google fuer diese Modellgeneration
     dokumentierte Obergrenze (Gemini-2.5-Pro-Klasse: 65535/65536
     Ausgabe-Token, von den Flash-Varianten derselben Generation
     geteilt). Bei rund 33 Token je Position ergibt das rund 1985
     Positionen Spielraum - selbst ohne den zusaetzlichen Gewinn durch
     thinkingBudget:0 weit ueber jedes realistische Schweizer
     NPK-Angebot hinaus, nicht nur ueber den einen gemeldeten Fall.

Der MAX_TOKENS-Rueckfall aus v3.40 bleibt unveraendert stehen - als
Sicherheitsnetz fuer den theoretisch weiterhin moeglichen,
pathologischen Ausreisser. Das Prinzip "keine geratenen Positionen"
(CLAUDE.md Abschnitt 78.5) bleibt strikt eingehalten: entweder die
vollstaendige, valide Liste, oder eine ehrliche Fehlermeldung - nie
eine abgeschnittene oder erfundene.

Live im Produktivprojekt (nfgryuzkpwjfmdlmevuy) deployt: Version 13,
status "ACTIVE".

2.2 Bewusst NICHT gebaut
------------------------------------
PDF-Aufteilung/Chunking ueber mehrere Gemini-Aufrufe hinweg. Das waere
eine deutlich groessere, stoeranfaelligere Infrastruktur (PDF-Zerlegung
in der Deno-Laufzeit, mehrere aufeinanderfolgende Aufrufe, Zusammen-
fuehren/Entdoppeln, Umgang mit Teilfehlern) fuer ein Problem, das die
einfache Anhebung der Obergrenze bereits mit sehr grossem
Sicherheitsabstand loest - die im Projekt wiederholt angewandte Regel,
nicht fuer einen nicht konkret belegten Bedarf zu bauen.

2.3 Kein Client-Code veraendert
------------------------------------
recognizePhoto() (js/17-ausmass.js) und ihr Aufruf aus
js/63-angebote.js heraus sind unveraendert - der ganze Fix liegt
serverseitig in der Edge Function. Keine der zwoelf Massaufnahme-
Fachdateien, kein Produktionsablauf-Modul (js/44-js/60) ist im Diff.

6. OFFENE PUNKTE
================================================================

- Kein Live-Klicktest gegen Supabase/Gemini moeglich (siehe
  Abschnitt 3).
- thinkingBudget:0 ist ein Wunsch, keine Garantie - Googles eigene
  Dokumentation sagt ausdruecklich, dass diese Modellgeneration
  volles Abschalten des Denkens nicht unterstuetzt; der tatsaechliche
  Tokenverbrauch dafuer ist von hier aus nicht messbar.
- 65536 Token decken jedes realistische Schweizer Angebot mit sehr
  grossem Abstand, aber nicht jedes denkbare Dokument - das ist die
  bewusste, dokumentierte Grenze, keine ungeprueft gelassene Annahme.
  Ein noch groesseres PDF wuerde weiterhin die ehrliche MAX_TOKENS-
  Meldung ausloesen statt eines Absturzes oder einer erfundenen Liste.
- Aus Abschnitt 145.9/3.40-Bericht unveraendert offen:
  pruefstand-angebote-v3-34.js, pruefstand-leistungen-v3-37.js,
  pruefstand-medien-am-ende-v2-75.js, pruefstand-angebot-pdf-v3-38.js
  und pruefstand-angebot-pdf-erkennen-v3-39.js bleiben mit ihren
  vorbestehenden, von dieser Runde unabhaengigen, versionsstand-/
  diff-gebundenen Selbstpruefungs-Abweichungen offen - jeder weitere
  Versionssprung wird voraussichtlich einen weiteren, gleichartigen
  Fall zu dieser Liste hinzufuegen.
