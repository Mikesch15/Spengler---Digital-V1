1. AUSGANGSLAGE
================================================================

Rueckmeldung des Betriebs: "klappt nicht mit positionen auslesen aus den
pdf, bitte ueberpruefen... so sehen unsere offerten aus...", mit einem
Bildschirmfoto des exakten Fehlerdialogs in der App ("Fehler bei der
Erkennung: Server antwortete mit Status 502: Antwort der KI konnte nicht
als Liste gelesen werden.") und einer echten, 13-seitigen Offerte im
Schweizer NPK-Format mit rund 90 einzeln nummerierten Positionen
(Offerte_18191_Steildachsanierung_Alpeneggstrasse_22_Bern). Mit "so sehen
unsere offerten aus" ist dieses dichte, reale Dokument ausdruecklich als
Normalfall benannt, nicht als Sonderfall.

Root Cause, belegt ueber die Produktivlogs (mcp__Supabase__query_logs,
Zeitstempel 2026-09-10T05:16:46Z): die Edge Function
extract-offer-positions rief Gemini mit maxOutputTokens: 3000 auf. Bei
rund 30-35 Ausgabe-Token je Position und rund 90 Positionen im
gemeldeten Dokument (~2970-3000 Token) wurde die JSON-Antwort mitten im
Array abgeschnitten und liess sich nicht mehr als gueltiges JSON parsen -
genau der gemeldete 502-Fehler.

2. TATSAECHLICH UMGESETZTE AENDERUNGEN
================================================================

2.1 Edge Function extract-offer-positions - v11 auf v12
----------------------------------------------------------
Live im Produktivprojekt (nfgryuzkpwjfmdlmevuy) verifiziert ueber
mcp__Supabase__list_edge_functions/get_edge_function: version 12,
status "ACTIVE", updated_at 1789023178651.

Zwei Aenderungen, beide zielgerichtet auf den belegten Fehler:

  1. maxOutputTokens: 3000 -> 8192. Bei 30-35 Token je Position deckt
     das rund 248 Positionen ab - klarer Sicherheitsabstand ueber das
     gemeldete Dokument (~90 Positionen) hinaus, ohne das Limit
     grundlos zu ueberdimensionieren.
  2. finishReason wird jetzt aus der Gemini-Antwort ausgelesen und beim
     JSON-Parse-Fehlschlag unterschieden: bei finishReason ===
     "MAX_TOKENS" kommt eine spezifische, handlungsanweisende deutsche
     Meldung ("Das Dokument enthaelt zu viele Positionen fuer eine
     einzelne Erkennung - die Antwort der KI wurde mitten im Satz
     abgeschnitten. Bitte das Dokument in kleineren Abschnitten
     hochladen oder die Positionen fuer diesen Teil von Hand
     erfassen.") statt der bisherigen generischen Meldung. Jeder andere
     Parse-Fehler faellt unveraendert auf die bestehende generische
     Meldung zurueck - keine neue Fehlerkategorie fuer echte
     Fehlfunktionen erfunden.

Der Erfolgspfad (JSON.parse gelingt, Array wird zurueckgegeben) ist
unveraendert. Keine geratenen/rekonstruierten Positionen aus einer
abgeschnittenen Antwort - das bestehende Prinzip "keine geratenen
Positionen" (CLAUDE.md Abschnitt 78.5) bleibt strikt eingehalten:
entweder die vollstaendige, valide Liste, oder eine ehrliche
Fehlermeldung.

6. OFFENE PUNKTE
================================================================

- Kein Live-Klicktest gegen Supabase moeglich (siehe Abschnitt 3).
- 8192 Token decken das gemeldete Dokument mit klarem Sicherheitsabstand

  ist eine bewusste, begruendete Grenze, keine ungeprueft gelassene

  bekaeme die neue, spezifische MAX_TOKENS-Meldung statt eines
  unklaren 502.
